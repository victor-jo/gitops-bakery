## The nine items

| # | Problem (file) | Effect on a user | Fix | Test that pins it |
|---|---|---|---|---|
| 1 | The root PAT is passed as a `kubectl exec` argument (`src/steps/gitlab-auth.ts:24`), and `ExecError` prints the whole command line (`src/lib/exec.ts:10`) | Other local users can read the token in `ps`. If the step fails, the token is printed to the terminal and may end up in a pasted bug report | Send the Ruby script on stdin (`kubectl exec -i … -- gitlab-rails runner -`, falling back to `sh -c 'cat > /tmp/pat.rb && gitlab-rails runner /tmp/pat.rb; rm -f /tmp/pat.rb'` if `-` is not supported). Add `redact?: string[]` to `ExecOptions`, which masks those values in `ExecError` | `ExecError masks redacted values`; `PAT step never puts the token in argv` (fake `run` records argv) |
| 2 | `createApp` uses `ensureProject`, so it takes over an `apps/<name>` that exists in GitLab but not in state (`src/apps/lifecycle.ts:52,56`) | A repo made by hand or left from a crash is adopted, and a later failure's rollback deletes it for good | New `GitLab.createProject(group, name)`. It fails with `GitLab project apps/<n> already exists; delete it or pick another name` when the path is taken. Rollback deletes only the projects this call created | `createApp refuses an existing GitLab project and deletes nothing`; `rollback removes only created projects` |
| 3 | An interrupted `git clone` leaves a partial `cache/garage-v2.2.0`, and `existsSync` then skips the clone forever (`src/steps/garage.ts:104`) | `install` resume is stuck until someone deletes the folder by hand | Clone into `<dir>.tmp-<pid>`, then rename. Treat the cache as valid only if `script/helm/garage/Chart.yaml` exists; otherwise remove it and clone again | `garageChartReady` returns false for a dir without Chart.yaml; `prepareGarageChart` reclones (fake `run`) |
| 4 | A helm release left in `pending-install` or `pending-upgrade` (helm killed mid-install) makes every rerun fail with `another operation (install/upgrade/rollback) is in progress` (`src/lib/helm.ts`) | A frozen lab with an opaque error | Before `upgrade --install`, read `helm status <rel> -o json`. On a `pending-*` status, stop with a message naming the release and the exact recovery commands (`helm rollback` for pending-upgrade, `helm uninstall` for pending-install), then "rerun install". No automatic uninstall, because it could delete PVC-backed data | `helmUpgrade stops with guidance on pending-install` (fake `run` returns status JSON) |
| 5 | The printed `claude mcp add …` fallback is joined with spaces, unquoted (`src/steps/claude.ts:40`) | Copy-pasting breaks when the checkout path contains a space | `shellQuote(args)`: single-quote any arg that is not `[A-Za-z0-9@%+=:,./_-]+` | `printed command quotes a path with spaces` |
| 6 | `deleteApp` frees the port at once, but Argo CD prunes the old Service later, and namespace `app-<name>` is left behind (`src/apps/lifecycle.ts`) | Re-creating within the window gets `provided port is already allocated`; old namespaces pile up | After removing the Application file and refreshing `service-root`, wait (up to 3 min) until Application `<name>` is gone. Then delete namespace `app-<name>` and release the port last | `deleteApp releases the port only after the Application is gone`; `deleteApp deletes the app namespace` (fake argocd/kube) |
| 7 | With no `state.json`, `uninstall` invents a new random name (`loadState` auto-creates) and cannot find the real cluster (`src/cli.ts:80`) | Lost state leaves an orphan cluster, about 8 GiB, that the tool can't remove | `uninstall [--cluster <name>]`. It never creates state. Without state it lists kind clusters whose names match the bakery word lists: exactly one is offered, several make it ask for `--cluster`, none means nothing to delete. `readState()` returns `undefined` instead of creating | `pickUninstallTarget` cases: state present, one candidate, several, none, explicit `--cluster`; `uninstall does not create state.json` |
| 8 | `doctor` says `✓ Ready to install` while the lab is already running (`src/cli.ts:68`) | Misleading: it suggests nothing is installed | When this lab's cluster exists: `✓ Lab <name> is running (ports are in use by it)`, plus the `status` hint | `doctor message reflects a running lab` (pure `doctorSummary(report, running)`) |
| 9 | Docs overstate things: `docs/mcp-tools.md:30` "everything created so far is removed", and spec line 134 says `create_app` "adds webhooks" | Readers believe behavior that does not exist | After item 2, mcp-tools says rollback removes only what that call created. The spec row is updated to the ci-refresh design | grep check in the task |

## Review Focus
1. The PAT is never visible in argv, logs or errors, even when the toolbox exec fails.
2. Delete followed by an immediate create of the same name works end to end.
3. `uninstall` never deletes a kind cluster that is not a bakery lab.
4. Resume after Ctrl-C at any step ends either in success or in a message that says exactly what to run.
5. Existing labs installed by v0.1.0 keep working after upgrading the CLI: the same state and secrets layout, and no forced reinstall.
